01 · Contexto

O que é o Diagrama de Classes?

Lembra da grande divisão da UML entre diagramas estruturais e de comportamento? O Diagrama de Classes é o principal representante dos diagramas estruturais. Ele responde: "Como o sistema está organizado por dentro?"

Diagrama de Classes fica dentro dos Diagramas de Estruturas.

Um Diagrama de Classes é um modelo estático — ele não mostra o que acontece no tempo, mas sim o que existe: as classes do sistema, seus atributos, suas operações e como elas se relacionam entre si.

Para que serve?

  • Ajuda a compreender os requisitos do domínio do problema.
  • Descreve exatamente como o sistema funciona internamente.
  • Mostra a estrutura e hierarquia de herança entre classes.
  • Serve de base para a geração de código em linguagens OO como Java, Python, C#...
02 · Conceitos Fundamentais

Orientação a Objetos & Classes

Antes de falar do diagrama, precisamos solidificar três conceitos da OO que aparecem em toda classe UML.

Analogia: a fôrma de biscoito

Classe é a fôrma (o molde). Objeto é o biscoito em si. Uma única fôrma "Cachorro" pode criar infinitos objetos: Rex, Bolinha, Totó — cada um com seus próprios valores de atributos (nome, raça, peso), mas todos compartilhando o mesmo comportamento (latir, andar, brincar).

Classe

Representa a abstração de um conjunto de objetos do mundo real que possuem comportamentos e características comuns. Por exemplo: a classe Cachorro abstrai todos os cachorros possíveis.

Atributos

São as características que os objetos de uma classe possuem, mas cada objeto assume valores diferentes. São os dados que o objeto carrega.

  • Classe Cachorro → atributos: nome, raça, peso
  • Classe Cliente → atributos: cpf, nome, sexo
  • Cada cachorro tem seu próprio nome — por isso é um atributo, não um método.

Operações (e Métodos)

São as ações que os objetos sabem fazer. Operação é o nome da ação (o contrato); método é a implementação interna (o código em si). No diagrama UML, usamos o termo "operação".

  • Classe Cachorro → operações: latir( ), andar( ), brincar( )
  • As operações são tudo o que os objetos fazem, e nada além disso.
  • O método é o algoritmo interno — ex: o código de public int somar(int a, int b){ return a+b; } é o método da operação somar.
Resumo rápido: Atributo = o que o objeto TEM. Operação = o que o objeto FAZ. Método = como ele faz (o código por dentro).

04 · Encapsulamento

Visibilidade — Encapsulamento

O símbolo que antecede cada atributo ou operação indica o seu nível de acessibilidade — ou seja, quem pode ver e usar aquele elemento. Isso é o encapsulamento em ação.

+
Public (Público)
Qualquer classe do sistema pode acessar
#
Protected (Protegido)
Apenas a própria classe e suas subclasses
−
Private (Privado)
Apenas a própria classe. O mais indicado para atributos!
~
Package (Pacote)
Classes do mesmo pacote podem acessar
SímboloNomeAtributosOperações
+ Public Qualquer classe pode manipular o atributo. Evitar usar para atributos. Funcionalidades visíveis por todas as classes. Mais comum para operações.
− Private Somente a própria classe. Indicado na maioria dos casos para atributos. Funcionalidades internas de apoio da própria classe.
# Protected A classe e suas subclasses. Funcionalidades que precisam ser estendidas por subclasses (frameworks).
~ Package Classes do mesmo pacote. Funcionalidades de apoio a outras classes do mesmo componente.
Analogia: o cofre da empresa

Private (−) é como o cofre do diretor — só ele abre. Protected (#) é como a sala dos gerentes — o diretor e seus herdeiros entram. Public (+) é a recepção — qualquer um acessa. Package (~) é o andar do escritório — quem trabalha naquele setor entra.

Regra de ouro: Na prática, todos os atributos devem ser privados (−). O acesso a eles é feito por métodos públicos (getters e setters). Isso é o princípio do encapsulamento!
05 · Relacionamento

Herança — Generalização / Especialização

A herança é representada por uma seta com ponta triangular vazia apontando da subclasse para a superclasse. A leitura é sempre "é um".

Se Gerente é um Funcionário → então Gerente herda todos os atributos e operações (não privadas) de Funcionário. Toda instância de Gerente pode ser usada em qualquer lugar que se espera um Funcionário.

Herança: Pessoa_Fisica e Pessoa_Juridica herdam os atributos e operações de Cliente.

O que é herdado?

Todos os atributos e operações não privados da superclasse ficam disponíveis na subclasse automaticamente. No exemplo: Pessoa_Fisica tem CPF, RG, sexo (próprios) + nome, uf, CEP, realizarCompra(), realizarTroca() (herdados de Cliente).

Efeito no código: Quando o diagrama de classes é traduzido para código (Java, Python...), a herança gera automaticamente herança de código e polimorfismo — o objeto filho pode ser tratado como o pai.
06 · Relacionamentos

Associações — Como as Classes se Conectam

Associação é a forma como objetos de uma mesma classe ou de classes diferentes se conectam e colaboram. É representada por uma linha entre as classes, podendo ter setas (direção de navegação), multiplicidades, nomes e papéis.

Associação Simples (→)

Linha com seta em uma direção. A indica que A conhece B, mas B não necessariamente conhece A.

Associação Bidirecional (↔)

Linha com setas nos dois sentidos ou sem seta. A conhece B e B conhece A.

Agregação (◇→)

Diamante vazio no "todo". Relação todo-parte fraca — as partes existem sem o todo.

Composição (◆→)

Diamante preenchido no "todo". Relação todo-parte forte — partes não existem sem o todo.

Nome, Direção de Leitura e Papéis

Nome da associação ("Contrata"), direção de leitura (▶) e papéis nas extremidades (contratante, contratado).

  • Nome da associação: verbo que descreve o relacionamento. Ex: "Contrata", "Trabalha".
  • Direção de leitura (▶): indica em qual sentido o nome deve ser lido.
  • Papéis: o papel que cada classe desempenha no relacionamento. Ex: "contratante" e "contratado".
07 · Multiplicidade

Multiplicidade — Quantos objetos se relacionam?

A multiplicidade define quantos objetos de uma classe podem se relacionar com objetos da outra classe. É escrita nas extremidades da linha de associação.

NotaçãoSignificado
0..1No mínimo zero, no máximo um. O relacionamento é opcional — pode ou não existir, mas se existir é com apenas um objeto.
1..1 ou 1Exatamente um. Obrigatório e único.
0..* ou *Zero ou muitos. Pode haver nenhum ou vários.
1..*Um ou muitos. Pelo menos um objeto deve estar envolvido.
2..5No mínimo 2, no máximo 5 objetos.
Regra de ouro: Se o início da multiplicidade é 1 (ex: 1, 1..1, 1..*), isso indica participação obrigatória. Se começa com 0 (ex: 0..1, 0..*), a participação é opcional.

Tipos de Conectividade

ConectividadeExtremo AExtremo BExemplo
Um para um0..1 ou 10..1 ou 1Pessoa ↔ CPF
Um para muitos0..1 ou 1* ou 1..* ou 0..*Departamento → Funcionários
Muitos para muitos* ou 1..** ou 1..*Aluno ↔ Disciplina

08 · Tipos de Associação

Associação Binária, Ternária e Unária

Associação Binária

A mais comum. Conecta exatamente duas classes por meio de uma linha. Exemplo clássico: Cliente possui Pedido de Venda.

Cliente
- nome : String
- sexo : char
- data_nascimento : Date
 
0 a muitos pedidos
Pedido de Venda
 
 

Associação binária: Cliente possui de 0 a muitos Pedidos de Venda.

Classe Associativa

Quando uma associação tem multiplicidade * nos dois lados (muitos para muitos), frequentemente precisamos guardar dados sobre a associação em si. Para isso criamos uma classe associativa, ligada à linha de associação por uma linha tracejada.

Exemplo: Pessoa trabalha em Empresa

Uma Pessoa pode trabalhar em muitas Empresas (*). Uma Empresa pode ter muitos Funcionários (*). O salário e a dataContratação não pertencem nem à Pessoa nem à Empresa — pertencem ao vínculo entre eles. Por isso criamos a classe associativa Emprego para guardar esses dados.

Classe associativa Disciplina_Curso: guarda dados do vínculo entre Curso e Disciplina.

Importante: Uma classe associativa pode ser substituída por uma classe ordinária comum, sem perda de informação. Basta transformar a linha tracejada em duas associações diretas (com multiplicidades). A aula mostra o exemplo Pessoa → Emprego → Empresa.

Associação Ternária

Quando três classes precisam se relacionar ao mesmo tempo, usamos uma associação ternária. É representada por um losango no centro, com linhas para cada uma das três classes.

Exemplo: Técnico usa Computador em Projeto

Um técnico usa exatamente um computador para cada projeto. Cada computador pertence a um técnico para cada projeto. Um técnico pode trabalhar em muitos projetos e usar computadores diferentes em cada um. Esse cenário não pode ser modelado com associações binárias simples — precisa de uma ternária.

Associação Unária (Reflexiva)

Ocorre quando uma classe se relaciona consigo mesma — objetos da mesma classe interagem entre si. O exemplo clássico: um Empregado pode supervisionar outros Empregados.

Cuidado: A associação reflexiva não significa que um objeto se associa a ele próprio (um empregado não supervisiona a si mesmo). Indica que objetos da mesma classe se associam entre si — supervisor e supervisionado são instâncias diferentes de Empregado.
Funcionários
- código : int
- nome : char
- codChefe : int
 

↖ A classe Funcionário tem uma autoassociação chamada "Chefia" com multiplicidade 0..* — um funcionário pode chefia 0 a muitos outros funcionários.

09 · Relacionamentos

Agregação versus Composição

Estas são as duas formas de relação todo-parte na UML. A diferença essencial é a força do vínculo: a parte pode existir sem o todo?

◇ Agregação — todo-parte FRACA

Diamante vazio (◇) no lado do "todo". Semântica: "contém".

  • O todo existe sem as partes
  • As partes existem sem o todo
  • Não há dependência de ciclo de vida

Ex: Carro (todo) ◇→ Pessoa (passageiro). Se o carro sumir, a pessoa continua existindo.

Palavra-chave: "tem", "possui", "contém" — mas ambos vivem independentemente
◆ Composição — todo-parte FORTE

Diamante preenchido (◆) no lado do "todo". Semântica: "é composto de".

  • As partes não existem sem o todo
  • As partes pertencem a somente um todo
  • A remoção do todo implica na remoção das partes

Ex: Carro (todo) ◆→ Peças. As peças de um carro específico não fazem sentido isoladas.

Palavra-chave: "é parte de", "não existe sem" — dependência de ciclo de vida
CaracterísticaAgregação ◇Composição ◆
DependênciaObjetos vivem separadamentePartes dependem do "contêiner"
Símbolo UMLLosango vazio ◇Losango preenchido ◆
Exemplo (aula)Turma e Alunos / Biblioteca e LivrosCasa e Cômodos / Carro e Motor
ExclusividadeParte pode pertencer a vários todosParte pertence a somente um todo

Gabarito dos exercícios da aula

◇ Turma e Alunos → Agregação
Os alunos existem mesmo sem a turma. Se a turma acabar, os alunos continuam sendo alunos.
◆ Carro e Motor → Composição
O motor não faz sentido existir sem o carro ao qual pertence. A remoção do carro implica remoção do motor.
◇ Departamento e Funcionários → Agregação
Funcionários existem independentemente do departamento. Um funcionário pode ser transferido.
◇ Biblioteca e Livros → Agregação
Livros existem fora da biblioteca. Podem ser emprestados, vendidos, existir em outras bibliotecas.
◆ Pedido e Itens → Composição
Um item de pedido só existe enquanto o pedido existir. Se o pedido for cancelado, os itens deixam de existir.
10 · Relacionamento

Dependência

Dependência é representada por uma linha tracejada com seta (- - - →). Ela deixa explícito que mudanças em uma classe podem gerar consequências em outra. É o relacionamento mais fraco da UML.

Quando ocorre dependência?

  • Classe A chama métodos de classe B
  • Classe A tem operações que retornam objetos de classe B
  • Classe A tem operações que recebem como parâmetro objetos de classe B
  • Outros relacionamentos (como associação com navegação) implicitamente determinam dependência
Dica: A dependência é transitiva — se A depende de B e B depende de C, então A depende de C indiretamente. Quanto menos dependências, mais desacoplado e manutenível é o sistema.

Restrições sobre Associações

{subset} — Subconjunto
Indica que uma associação é um subconjunto de outra. No exemplo da aula: "Administra" é um subconjunto de "Reside" — ou seja, toda pessoa que administra um edifício também reside nele.
Notação: {subset} entre as duas associações
{xor} — Exclusivo
Indica que apenas um dos relacionamentos pode existir ao mesmo tempo. No exemplo: uma ContaBancária pertence a uma Pessoa ou a uma Instituição — nunca às duas ao mesmo tempo.
Notação: {xor} entre as duas associações
11 · Elementos Especiais

Propriedades Estáticas, Derivadas e Classes Abstratas

Propriedades e Operações Estáticas (sublinhadas)

Propriedades estáticas não são instanciadas nos objetos — elas pertencem à classe em si, não a cada objeto individualmente. São acessadas diretamente na classe, sem precisar criar um objeto.

Pedido
- data : Date
- numero : int
- valor : Money
+ finaliza() : void
+ getProximoNumero() : int

O método getProximoNumero() está sublinhado — é estático. Você pode chamá-lo como Pedido.getProximoNumero() sem criar um objeto Pedido. Ele provavelmente acessa um contador global da classe.

Atributos e operações estáticas são sublinhadas no diagrama de classes.

Propriedades Derivadas (marcadas com /)

São propriedades que não existem como atributos reais no banco de dados — elas são calculadas (derivadas) a partir de outros atributos. O símbolo "/" indica derivação.

Período
+ inicio : Date
+ fim : Date
+ /duracao : int
 

duracao é derivada: duracao = fim - inicio. Ela não precisa ser armazenada no banco — é sempre calculada. O "/" avisa ao programador para não criar uma coluna para ela.

Classes Abstratas (nome em itálico)

Uma classe abstrata é uma classe que não pode ter instâncias diretamente — você nunca cria um objeto dela. Ela existe para ser herdada por subclasses concretas, que implementarão seus métodos abstratos.

  • Usualmente têm operações abstratas — sem implementação interna.
  • As subclasses concretas implementam o comportamento específico.
  • São identificadas pelo nome em itálico no diagrama.
Animal
 
+ fala() : void
herda ↓
Cachorro
 
+ fala() : void
//latir
Gato
 
+ fala() : void
//miar

Animal é abstrata (itálico) — Cachorro e Gato implementam fala() com comportamentos específicos.

12 · Processo

Como Encontrar as Classes?

A etapa mais difícil é saber o que vira classe. A aula ensina a procurar no documento de requisitos e nos modelos de casos de uso pelos seguintes tipos de elementos:

TipoDescriçãoExemplo
AgentesPessoas e organizações que interagem com o sistemaFuncionário, Empresa, Cliente
PapéisFunções que entidades assumem no sistemaAutor, Contratante, Analista
ObjetosCoisas do domínio que são informações compostasLivro, Contrato, Produto, Curso
EventosAcontecimentos que ocorrem durante a operaçãoLocação, Matrícula, Reserva, Pedido
LugaresContextos físicos ou lógicos do problemaLoja, Filial, Departamento
EstruturasEstruturas definidas no problemaEstoque, Catálogo, Portfólio
Por isso a Análise é tão importante! Um levantamento de requisitos bem feito — com casos de uso, entrevistas e documentação — é a base para identificar todas as classes corretamente.

Os 3 Níveis de Abstração do Modelo de Classes

① Domínio
Construído na fase de análise. Representa os termos do negócio. Não considera restrições de tecnologia. Só mostra o nome da classe (sem tipos específicos de linguagem).
Ex: ContaBancária só com o nome
② Especificação
Adiciona atributos e operações conforme a solução de software escolhida. Novos tipos de classes surgem para estruturar a solução técnica.
Ex: ContaBancária com criar(), bloquear(), número, saldo...
③ Implementação
Detalha os tipos de dados específicos da linguagem, visibilidades e assinaturas completas. Está pronto para virar código.
Ex: -número : String, +creditar(in valor : Quantia)

Dicas da Profª

  • Comece com um diagrama simples (apenas classes, atributos, operações e associações).
  • Use os recursos avançados (restrições, propriedades derivadas, etc.) somente quando for realmente necessário.
  • Valide o modelo com os requisitos: o diagrama deve ser capaz de responder às perguntas do sistema.

Todo-parte forte. Partes morrem com o todo. Ex: Pedido e Itens.

Dependência

- - → linha tracejada. Mudança em B pode afetar A. Relacionamento mais fraco.

Atributos/operações da classe, não dos objetos. Acessados sem instanciar: Classe.metodo()

1. Qual é a diferença entre Operação e Método no contexto OO?
Operação é o nome/contrato da ação que um objeto pode executar (aparece no diagrama UML). Método é a implementação interna — o código em si (o algoritmo). A operação é o "o quê"; o método é o "como".

2. Quais são os 4 níveis de visibilidade? Para cada um, diga o símbolo e quem pode acessar.
+ (Public): qualquer classe do sistema.
− (Private): somente a própria classe. Indicado para atributos.
# (Protected): a própria classe e suas subclasses.
~ (Package): classes do mesmo pacote.

3. O que é multiplicidade? O que significa 1..* e como é diferente de 0..*?
Multiplicidade define quantos objetos de uma classe participam de um relacionamento com outra.

1..* significa "pelo menos um e no máximo muitos" — a participação é obrigatória (mínimo 1).
0..* significa "nenhum ou muitos" — a participação é opcional (pode ser zero).

4. Qual a diferença entre Agregação e Composição? Dê um exemplo de cada.
Agregação (◇): relação todo-parte FRACA. As partes existem sem o todo. Ex: Biblioteca e Livros — livros existem fora da biblioteca.

Composição (◆): relação todo-parte FORTE. As partes não existem sem o todo; a remoção do todo implica remoção das partes. Ex: Pedido e Itens — os itens só existem enquanto o pedido existir.

5. O que é uma Classe Associativa? Quando ela é necessária?
Uma classe associativa surge quando uma associação do tipo muitos-para-muitos (*→*) precisa armazenar atributos próprios do relacionamento. Por exemplo: Pessoa trabalha em Empresa — o salário e a data de contratação não pertencem nem à Pessoa nem à Empresa, mas ao vínculo entre elas. Por isso criamos a classe Emprego. É representada por uma reta tracejada saindo do meio da associação.

6. O que são propriedades derivadas? Como são marcadas no diagrama?
São propriedades que não existem como atributos armazenados — são calculadas a partir de outros atributos. Marcadas com o símbolo /. Exemplo: a classe Período tem inicio e fim (armazenados). A propriedade /duracao é derivada: duracao = fim − inicio. Ela não precisa de uma coluna no banco de dados.

Uma classe abstrata é uma classe que não pode ser instanciada diretamente — você não pode criar objetos dela. Ela existe para ser herdada por subclasses concretas, que implementarão seus métodos abstratos. É identificada pelo nome em itálico no diagrama. Exemplo: a classe Animal com o método fala() — Cachorro implementa latir, Gato implementa miar.
