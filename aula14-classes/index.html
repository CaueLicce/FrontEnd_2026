01 · Contexto

O que é o Diagrama de Classes?

Lembra da grande divisão da UML entre diagramas estruturais e de comportamento? O Diagrama de Classes é o principal representante dos diagramas estruturais. Ele responde: "Como o sistema está organizado por dentro?"

Diagrama de Classes fica dentro dos Diagramas de Estruturas.

Um Diagrama de Classes é um modelo estático — ele não mostra o que acontece no tempo, mas sim o que existe: as classes do sistema, seus atributos, suas operações e como elas se relacionam entre si.

Para que serve?

  • Ajuda a compreender os requisitos do domínio do problema.
  • Descreve exatamente como o sistema funciona internamente.
  • Mostra a estrutura e hierarquia de herança entre classes.
  • Serve de base para a geração de código em linguagens OO como Java, Python, C#...
02 · Conceitos Fundamentais

Orientação a Objetos & Classes

Analogia: a fôrma de biscoito

Classe é a fôrma (o molde). Objeto é o biscoito em si. Uma única fôrma "Cachorro" pode criar infinitos objetos: Rex, Bolinha, Totó — cada um com seus próprios valores de atributos, mas todos compartilhando o mesmo comportamento.

Classe

Representa a abstração de um conjunto de objetos do mundo real que possuem comportamentos e características comuns.

Atributos

São as características que os objetos de uma classe possuem, mas cada objeto assume valores diferentes.

  • Classe Cachorro → atributos: nome, raça, peso
  • Classe Cliente → atributos: cpf, nome, sexo

Operações (e Métodos)

São as ações que os objetos sabem fazer. Operação é o nome da ação (o contrato); método é a implementação interna.

Resumo rápido: Atributo = o que o objeto TEM. Operação = o que o objeto FAZ. Método = como ele faz.

05 · Relacionamento

Herança — Generalização / Especialização

A herança é representada por uma seta com ponta triangular vazia apontando da subclasse para a superclasse. A leitura é sempre "é um".

Herança: Pessoa_Fisica e Pessoa_Juridica herdam os atributos e operações de Cliente.

O que é herdado?

Todos os atributos e operações não privados da superclasse ficam disponíveis na subclasse automaticamente.

Efeito no código: A herança gera automaticamente polimorfismo — o objeto filho pode ser tratado como o pai.
06 · Relacionamentos

Associações — Como as Classes se Conectam

Associação Simples (→)

A conhece B, mas B não necessariamente conhece A.

Associação Bidirecional (↔)

A conhece B e B conhece A.

Agregação (◇→)

Diamante vazio. Todo-parte fraca — partes existem sem o todo.

Composição (◆→)

Diamante preenchido. Todo-parte forte — partes não existem sem o todo.

  • Nome da associação: verbo que descreve o relacionamento.
  • Direção de leitura (▶): indica em qual sentido o nome deve ser lido.
  • Papéis: o papel que cada classe desempenha. Ex: "contratante" e "contratado".

08 · Tipos de Associação

Associação Binária, Ternária e Unária

Associação Binária

A mais comum. Conecta exatamente duas classes. Exemplo: Cliente possui Pedido de Venda.

Classe Associativa

Quando uma associação tem multiplicidade * nos dois lados, criamos uma classe associativa para guardar dados do vínculo.

Exemplo: Pessoa trabalha em Empresa

O salário e a dataContratação pertencem ao vínculo entre eles — por isso criamos a classe associativa Emprego.

Associação Ternária

Quando três classes precisam se relacionar ao mesmo tempo — representada por um losango central.

Associação Unária (Reflexiva)

Ocorre quando objetos da mesma classe se relacionam entre si. Ex: Empregado supervisiona outros Empregados.

Cuidado: Não significa que um objeto se associa a si mesmo — objetos diferentes da mesma classe se relacionam.
09 · Relacionamentos

Agregação versus Composição

◇ Agregação — todo-parte FRACA
Diamante vazio. As partes existem sem o todo.

Ex: Turma ◇→ Alunos. Se a turma acabar, os alunos continuam existindo.
"tem", "possui" — ambos vivem independentemente
◆ Composição — todo-parte FORTE
Diamante preenchido. As partes não existem sem o todo.

Ex: Pedido ◆→ Itens. Cancelado o pedido, os itens deixam de existir.
"é parte de", "não existe sem" — dependência de ciclo de vida
CaracterísticaAgregação ◇Composição ◆
DependênciaObjetos vivem separadamentePartes dependem do contêiner
Símbolo UMLLosango vazio ◇Losango preenchido ◆
ExemploTurma e Alunos / Biblioteca e LivrosCasa e Cômodos / Pedido e Itens

Gabarito dos exercícios da aula

◇ Turma e Alunos → Agregação
Os alunos existem mesmo sem a turma.
◆ Carro e Motor → Composição
O motor não existe sem o carro ao qual pertence.
◇ Departamento e Funcionários → Agregação
Funcionários existem independentemente do departamento.
◇ Biblioteca e Livros → Agregação
Livros existem fora da biblioteca.
◆ Pedido e Itens → Composição
Itens só existem enquanto o pedido existir.
10 · Relacionamento

Dependência

Representada por uma linha tracejada com seta (- - - →). Mudanças em uma classe podem gerar consequências na outra. É o relacionamento mais fraco da UML.

Quando ocorre?

  • Classe A chama métodos de classe B
  • Classe A tem operações que retornam objetos de B
  • Classe A tem operações que recebem como parâmetro objetos de B
Dica: Quanto menos dependências, mais desacoplado e manutenível é o sistema.
{subset} — Subconjunto
Uma associação é subconjunto de outra. Ex: "Administra" é subconjunto de "Reside".
Notação: {subset}
{xor} — Exclusivo
Apenas um relacionamento pode existir ao mesmo tempo. Ex: ContaBancária pertence a Pessoa ou Instituição.
Notação: {xor}
11 · Elementos Especiais

Propriedades Estáticas, Derivadas e Classes Abstratas

Propriedades Estáticas (sublinhadas)

Pertencem à classe em si, não a cada objeto individualmente. São acessadas diretamente na classe sem instanciar.

Pedido
- data : Date
- numero : int
- valor : Money
+ finaliza() : void
+ getProximoNumero() : int

getProximoNumero() está sublinhado — é estático. Chamado como Pedido.getProximoNumero() sem criar um objeto.

Propriedades Derivadas (/)

Calculadas a partir de outros atributos — não são armazenadas no banco de dados.

Período
+ inicio : Date
+ fim : Date
+ /duracao : int
 

/duracao = fim - inicio. Não precisa de coluna no banco — sempre calculada.

Classes Abstratas (nome em itálico)

Não podem ser instanciadas. Existem para ser herdadas por subclasses concretas.

Animal
 
+ fala() : void
herda ↓
Cachorro
 
+ fala() : void
//latir
Gato
 
+ fala() : void
//miar

Animal é abstrata (itálico) — Cachorro e Gato implementam fala() com comportamentos diferentes.

Os 3 Níveis de Abstração

① Domínio
Fase de análise. Termos do negócio, sem tecnologia.
Ex: ContaBancária só com o nome
② Especificação
Adiciona atributos e operações conforme a solução escolhida.
Ex: ContaBancária com criar(), bloquear()...
③ Implementação
Tipos da linguagem, visibilidades, assinaturas completas — pronto para código.
Ex: -número : String, +creditar(in valor : Quantia)
13 · Resumo

Tudo sobre o Diagrama de Classes

Estrutura da Classe

3 partições: Nome, Atributos, Operações. Notação: visibilidade nome : tipo

Visibilidade

+ público, − privado, # protegido, ~ pacote. Atributos quase sempre privados!

Herança

Seta triangular vazia → superclasse. Leitura: "é um". Herda tudo que não é privado.

Associação

Linha entre classes. Pode ter nome, papéis, direção de leitura e multiplicidade.

Multiplicidade

0..1, 1, *, 1..*, 0..*. Início em 1 = obrigatório. Início em 0 = opcional.

Classe Associativa

Necessária quando há * nos dois lados. Guarda atributos do vínculo.

Agregação ◇

Todo-parte fraca. Partes vivem sem o todo. Ex: Turma e Alunos.

Composição ◆

Todo-parte forte. Partes morrem com o todo. Ex: Pedido e Itens.

Dependência

- - → linha tracejada. Mudança em B pode afetar A. Relacionamento mais fraco.

Estático (sublinhado)

Pertence à classe, não aos objetos. Acessado sem instanciar.

Derivado (/)

Calculado de outros atributos. Não armazenado. Ex: /duracao = fim - inicio

Classe Abstrata

Nome em itálico. Não pode ser instanciada. Subclasses implementam seus métodos.

Operação é o nome/contrato da ação (aparece no diagrama). Método é a implementação interna — o código. Operação é o "o quê"; método é o "como".
